# Billing operations

This module implements manual-renewal paid access with hosted Flutterwave v3 checkout. The free library remains available according to each resource's content policy. Card numbers and mobile-money PINs are entered only at the provider. A browser redirect, client claim, or signed webhook by itself never activates access: the API queries the provider and checks the merchant account, transaction ID, reference, exact UGX amount, currency and successful state first.

## Local setup

1. Apply the version-controlled Prisma migrations and database role grants using the repository database setup instructions. Never reset a database with unverified data.
2. Create an ignored `.env.local` with the normal application settings. Obtain `FLUTTERWAVE_TEST_SECRET_KEY`, `FLUTTERWAVE_TEST_WEBHOOK_HASH`, and `FLUTTERWAVE_TEST_ACCOUNT_ID` from the same Flutterwave **test** account. Use test credentials only. Configure the v3 webhook URL as `/api/v1/payments/webhooks/flutterwave_v3` in the test dashboard. Do not send those values in chat or commit them.
3. Start the API and web app. The API remains available without payment credentials, but checkout returns 503. The initial platform policy deliberately has no approved paid price, so finance must approve and activate a policy version before creating a paid plan. No price or subscription offer is invented by the seed.
4. A finance user with the appropriate `BILLING_*` permission and recent MFA creates a monthly, quarterly or annual immutable plan version in the finance UI. Library plan prices must match the active policy. Publication and volume scopes require an existing published resource. A standalone publication uses the publication scope; a series can use a publication scope, and a single volume uses the volume scope.
5. Open `/?screen=pricing`, choose a plan, and complete the hosted **test** checkout. Uganda mobile money and card are offered by the provider for UGX, subject to the test account's enabled methods. The payment result screen can recheck an order. It shows pending state until the server confirms settlement.

Production checkout has an additional explicit gate: `NODE_ENV=production`, `BILLING_LIVE_ENABLED=1`, and a complete separate `FLUTTERWAVE_LIVE_*` credential set. The local and automated test paths never select live credentials. Activating live billing, public prices, tax wording, refund terms, merchant settlement account, and payment methods requires accountable business and finance approval. No automated test makes a live charge.

## Lifecycle and recovery

- `Idempotency-Key` is required for order creation, retry and refund request. An order is committed before calling the provider, with a unique merchant reference. If hosted checkout fails, the same key can request the same order and retry obtaining its link. Concurrent settlement is serialized by database row locks; one successful verification creates one invoice and paid entitlement.
- The current policy controls plan periods, grace days, reminders, refund window and dispute freezing. Renewal is **manual**. The code never charges a saved payment method or implies that provider recurring debit is available. Renewal extends from the current paid-through date. A plan change creates a separate paid subscription; the prior paid term remains valid and is marked to end at its paid-through date. No unapproved proration or credit is applied.
- The 15-minute billing job expires subscriptions, queues reminders and rechecks pending and paid payments plus submitted refunds. An advisory lock prevents overlapping job runners. The finance dashboard can start an on-demand, bounded reconciliation batch. `ReconciliationItem` and audit events retain exceptions for review. Review failed, reversed, disputed and mismatched payments before manual correction; never grant access from an unverified provider state.
- Refund submission requires an independent finance approver with recent MFA. Provider submission is deliberately at most once: a failed or uncertain submission stays `SUBMITTED` for operator investigation, because an idempotent provider refund retry has not been verified. A full refund revokes that order's entitlement only after the provider confirms settlement. Other free, institutional and complimentary entitlements remain independent.
- Disputes can freeze the associated paid entitlement under active policy. A different finance user resolves the case. A win requires fresh provider confirmation before reinstatement. Reversals revoke the associated paid order; all transitions are audited.
- Invoices and CSV statements are derived from verified paid orders. The statement explicitly flags tax treatment as pending review; it is not a statutory tax invoice. Finance totals use decimal strings to avoid integer precision loss in large aggregates.

## Verification

Run `npm run db:verify`, `npx vitest run tests/integration/billing.test.ts tests/unit/billing-gateway.test.ts`, and `npx playwright test tests/e2e/billing.spec.ts`. Integration tests use only the isolated `arata_techlibrary_test` database and a fake sandbox gateway. Provider response shape and live webhook delivery must be exercised separately with real **test** credentials before enabling a public paid offer. See `Documentation/Implementation/TEST_RESULTS.md` and `BLOCKERS.md` for the current evidence and remaining launch gates.
